**Audience:** New IT Engineers & Consultants at EY  
**Session Objective:** Understand Continuous Integration, Continuous Delivery/Deployment (CI/CD), Containerization, and Automated Governance using GitHub Actions & GHCR.

## 🎯 Step-by-Step Presentation Script

### Phase 1: The Enterprise Problem (00 - 05 min)
* **What to say:**
  > *"Welcome everyone! In enterprise IT consulting at EY, we often encounter legacy client systems where engineers manually FTP files, build containers locally on their laptops, or deploy without automated testing. What happens when a developer forgets to run unit tests or uses a compromised library? Outages and compliance violations.*
  >
  > *Today, we are going to demonstrate how modern teams solve this using **CI/CD with GitHub Actions and GitHub Container Registry (GHCR)**."*

* **Key Concept to highlight:**
  - **Shift-Left:** Catch bugs and security CVEs as early as possible in the development lifecycle before they reach staging or production.

---

### Phase 2: Pipeline Deep Dive (`.github/workflows/ci-cd.yml`) (05 - 12 min)
Open `.github/workflows/ci-cd.yml` on your screen and walk through the stages:

1. **Triggers (`on:`):**
   - Explain `push` vs. `pull_request` vs. `workflow_dispatch`.
   - Point out `workflow_dispatch`: allows manual execution directly from the GitHub UI for demos or ad-hoc runs.

2. **Least Privilege Permissions:**
   ```yaml
   permissions:
     contents: read
     packages: write
   ```
   *Explain why:* By default, workflows shouldn't have unnecessary write permissions. We only grant `packages: write` so the runner can publish container images to GHCR.

3. **Stage 1: Code Quality & Testing (`needs: []`):**
   - Runs `npm run lint` (syntax integrity).
   - Runs `npm test` (12 automated unit tests validating compliance rules).
   - Runs `npm audit` (automated dependency security check).

4. **Stage 2: Multi-Stage Docker Build & GHCR Release (`needs: code-quality-and-test`):**
   - Notice the `needs:` keyword! If Stage 1 fails, Stage 2 **never executes**. Broken code is never packaged into a Docker image.
   - Point out `${{ secrets.GITHUB_TOKEN }}`: No external secrets needed! GitHub automatically provisions an ephemeral token to authenticate with `ghcr.io`.
   - Highlight the **Immutable Tagging**: Images are tagged with the Git commit SHA (`sha-e7f41a9`), ensuring complete traceability for IT auditability.

---

### Phase 3: Live Pipeline Execution (12 - 18 min)
* **Live Action:**
  1. Make a small edit (e.g., in `package.json` bump version or change a comment).
  2. Commit and push:
     ```bash
     git add .
     git commit -m "feat: Add compliance control rule"
     git push
     ```
  3. Open your repository's **Actions** tab on projector/screen.
  4. Show the visual graph transitioning from queued ➔ yellow in-progress ➔ green checkmarks.
  5. Click into the workflow run and show the **Executive Step Summary**:
     - Point out the summary table automatically generated by the pipeline.
  6. Navigate to your GitHub profile/organization **Packages** tab and show the newly published Docker image on `ghcr.io`.

### Phase 4: Live App & Observability Walkthrough (18 - 25 min)
Launch the application locally or run the Docker container:
```bash
docker run -p 3000:3000 ghcr.io/<your-username>/ey-devops-dashboard:latest
```
Open **`http://localhost:3000`** in your browser.

1. **Show KPI Metric Cards:**
   - Compliance Governance (`96% OPTIMAL`).
   - Container Pod Health (`3/3 Replicas`).
   - P99 Latency with live sparkline (~18ms).
   - GHCR Package Registry metadata with exact Git Commit SHA.
2. **Tab 1 - Pipeline Visualizer:**
   - Shows the visual flowchart of the 5 pipeline stages.
3. **Tab 2 - Regulatory Assurance Checklist:**
   - Filter by SOC 2, ISO 27001, and CIS Benchmarks.
   - Click **"Run Compliance Audit"** to demonstrate on-demand verification.
4. **Tab 3 - Chaos Engineering & Observability:**
   - Click **"Simulate Incident"**!
   - Watch the red incident banner appear.
   - Point out how P99 latency spikes from 18ms to ~420ms, CPU gauge changes color, and Pod health switches to `2/3 Ready`.
   - Explain to the trainees: *"This is how modern SRE and Site Reliability Engineering works. Our health checks (`/api/health`) and observability metrics immediately catch anomalies."*
   - Click **"Auto-Remediate Pod"** to restore healthy state.
5. **Tab 4 - Audit Trail:**
   - Show the simulated live immutable log stream verifying every event.

### Phase 5: Common Questions & Answer Cheat Sheet (25 - 30 min)

**Q1: Why do we use GHCR (GitHub Container Registry) instead of Docker Hub?**  
*Answer:* GHCR is natively integrated into GitHub. It shares the same permission model, integrates with your organization's SSO/IAM, and requires zero third-party credentials or API keys inside GitHub Actions workflows.

**Q2: What is the difference between Continuous Delivery and Continuous Deployment?**  
*Answer:* In Continuous Delivery, every passing build produces a deployable artifact (like our Docker image in GHCR) ready for production, but might require an approval gate. In Continuous Deployment, the artifact is automatically pushed all the way to live production clusters without manual intervention.

**Q3: Why did we use a multi-stage Dockerfile?**  
*Answer:* In a standard Dockerfile, build tools, source code, and developer dependencies bloat the image to 500MB+ and introduce unnecessary CVE vulnerabilities. A multi-stage build only copies production dependencies into a bare Alpine runtime (~65MB), reducing the attack surface and download times.

**Q4: Why does our Docker container run as `USER node` instead of `root`?**  
*Answer:* Running containers as root is a major security risk. If an attacker exploits a vulnerability in the application, they could escape the container and obtain root control over the host Kubernetes node. Running as an unprivileged user adheres to CIS Benchmarks and EY security standards.
